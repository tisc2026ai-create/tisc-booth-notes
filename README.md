# TiSC 현장 상담 기록

휴대폰·노트북에서 상담 시작·종료 시각, 회사명, 메모와 명함 사진을 기록하는 정적 웹앱입니다. 현장에서 만든 기록 묶음을 분석 PC로 옮기는 첫 단계를 제공합니다.

화면 파일만 GitHub Pages에 게시합니다. 상담 데이터와 명함은 **입력한 기기의 해당 브라우저 IndexedDB**에 저장하며, GitHub로 전송하지 않습니다. 직원마다 기기와 브라우저의 기록이 따로 있습니다. 분석 PC에서 사이트에 접속하는 것만으로 다른 기기의 기록을 볼 수는 없습니다.

## 현장에서 사용하기

1. 인터넷이 연결된 상태에서 사이트를 처음 열고 화면이 준비된 것을 확인합니다. 오프라인 사용을 위해 같은 브라우저에서 한 번 새로고침해 둡니다.
2. 기록할 조를 선택하고, 녹음기와 휴대폰·노트북의 날짜·시각을 맞춥니다. 녹음 원본의 실제 시작 시각도 별도로 남깁니다.
3. 휴대폰에서는 `상담 목록`·`상담 입력`·`내보내기`로 화면을 전환합니다. 실제 대화가 시작할 때 `상담 시작 · 시간 기록`을 누르고 회사명·메모를 입력합니다. `사진 촬영` 또는 `사진첩에서 선택`으로 명함·명찰을 첨부하고, 사진을 눌러 확대해 확인합니다.
4. 상담 중 다른 회사가 문의하면 `다른 상담 추가`로 새 기록을 추가합니다. 기존 입력을 먼저 저장하며, 저장에 실패하면 상담 추가·전환을 중단하고 입력을 화면에 유지합니다. 기존 상담은 진행 중으로 유지됩니다. 입력 화면의 다른 진행 중 상담을 눌러 전환하거나, 새 문의를 종료한 뒤 `진행 중 상담으로 돌아가기`로 기존 상담을 이어갑니다. 시간 구간이 겹치는 상담은 녹음 분석 시 회사별 발언 확인이 필요하므로 메모로 구분해 두세요.
5. 대화가 끝나면 상담을 종료합니다. 목록에서 기록과 시각을 확인하고 필요하면 수정합니다.
   불필요한 기록은 목록에서 열고 `이 상담 삭제`를 누릅니다. 확인창에서 회사명·상담 시각·함께 지울 명함 장수를 확인하고 삭제하거나 취소합니다. 해당 상담과 첨부 사진만 지우며 다른 상담은 유지합니다. 앱에서 되돌릴 수 없으므로 보관할 기록은 먼저 ZIP으로 내보내세요. 다른 탭에서 기록이 바뀌면 삭제하지 않고 다시 확인하도록 안내합니다.
6. 쉬는 시간과 마감 때 기록을 ZIP으로 내보냅니다. 진행 중인 상담도 종료 시각 없이 포함하며, 다운로드 후 기록이나 사진을 자동 삭제하지 않습니다. 검색과 관계없이 선택한 날짜의 기록을 담으며, `모든 날짜 ZIP 백업`은 이 기기의 모든 날짜를 포함합니다. 같은 팀이라도 각 기기에서 따로 내보내세요. 다운로드한 파일이 실제로 생겼는지 확인하고, 분석 PC의 `현장 기록 가져오기`에서 열거나 별도 위치에 보관합니다.

시각은 기기 시계를 기준으로 기록합니다. 휴대폰의 시계가 녹음기와 다르면 상담 음성의 분할 위치도 어긋날 수 있습니다. 이 웹앱 자체는 음성을 녹음하지 않습니다.

전체 녹음과 개별 녹음 모두 같은 상담 시간·메모·명함 형식을 사용합니다. 전체 녹음은 분석 PC에서 팀과 실제 녹음 시작 시각을 맞춰 상담 구간에 연결하고, 개별 녹음은 해당 상담에 파일을 연결합니다. 녹음 원본은 현장 ZIP에 포함되지 않으므로 별도로 옮깁니다. 종료 시각이 없는 상담은 시간 확인 후 분석합니다.

서비스 워커가 준비된 뒤에는 인터넷 연결이 끊겨도 이미 받은 화면으로 기록할 수 있습니다. 최초 접속·화면 업데이트·GitHub Pages 게시에는 인터넷이 필요합니다. 시크릿 모드 대신 일반 브라우저를 사용하고, 현장에서 쓸 실제 휴대폰에서 비행기 모드와 재접속을 먼저 확인하세요.

## 파일로 옮기기

내보낸 ZIP에는 상담 데이터와 각 상담에 연결된 명함 이미지가 함께 들어갑니다. 상담 고유 ID를 유지하므로 다른 기기에서도 같은 상담을 식별할 수 있습니다. 분석 PC에서는 기록 묶음과 하루 녹음 원본을 함께 보관하면 됩니다.

ZIP 안의 `manifest.json`은 `schemaVersion: 1`, 내보낸 시각과 상담 목록을 담고, `cards/`에는 명함 이미지가 들어갑니다. 상담의 시작·종료 시각은 UTC ISO 형식이며 화면에서 현지 시각으로 표시합니다. 이 앱이 만든 비압축 ZIP만 가져올 수 있고, 파일 하나는 최대 256MiB입니다. 더 큰 묶음은 날짜를 나눠 내보냅니다. 사진은 JPG·PNG·WebP 형식을 사용합니다.

이 앱의 가져오기 기능은 내보낸 묶음을 검증한 뒤 기기에 복원합니다. 같은 ID의 상담은 수정 시각이 더 최신인 기록을 사용하고 오래된 기록은 유지하지 않습니다. 동일한 수정 시각에 다른 내용이나 명함이 있으면 전체 가져오기를 취소합니다. 여러 탭에서 같은 상담을 수정할 때도 처음 읽은 수정 시각을 확인해 최신 기록의 덮어쓰기를 막습니다. 가져오기 오류가 나면 원본 ZIP을 보관하고 원인을 확인하세요.

현장 웹앱에는 녹음 분할·음성 인식·명함 OCR·판매 검토 기능이 없습니다. 이 작업은 별도의 분석 PC 워크스페이스에서 진행합니다. 현장 ZIP을 가져온 뒤 해당 녹음을 연결하고 분석을 시작합니다.

## 로컬 실행과 검사

별도 빌드와 패키지 설치 없이 실행합니다. 이 디렉터리에서:

```sh
python3 -m http.server 8000
```

같은 PC의 브라우저에서 `http://localhost:8000`을 엽니다. HTML 파일을 더블클릭하는 `file://` 방식 대신 HTTP로 실행하세요. 서비스 워커는 HTTPS 또는 localhost 환경에서 사용합니다. 휴대폰 현장 사용은 게시된 HTTPS 주소로 확인합니다.

회귀 검사는 Node.js 24에서 실행합니다. 외부 npm 패키지는 설치하지 않습니다.

```sh
npm test
```

Google Chrome이 설치된 환경에서는 실제 브라우저의 기록·명함·파일 전달·오프라인 동작을 검사할 수 있습니다. 임시 프로필을 사용하므로 실제 상담 기록에 접근하지 않습니다.

```sh
node tools/browser-check.mjs
```

브라우저 검사는 저장·새로고침 유지, 명함 ZIP 왕복, 중복·충돌·오래된 탭의 덮어쓰기 방지, 저장 실패 시 상담 추가·전환 중단, 전환 직전 수정 저장, 시작·종료·동시 상담·사진 선택·진행 중 상담 내보내기·가져오기, 모바일 화면 전환·가로 넘침과 오프라인 재접속을 확인합니다. 실제 휴대폰 카메라와 명함 글씨 판독 품질은 별도로 확인하세요. 명령 뒤에 게시 주소를 붙이면 같은 검사로 배포 환경도 확인할 수 있습니다.

## GitHub Pages 게시

게시할 계정은 `tisc2026ai-create`, 저장소 이름은 `tisc-booth-notes`입니다. **이 디렉터리의 내용만 별도 저장소 루트로** 올립니다. 상위 프로젝트나 회사 팸플릿, 고객 기록, 녹음 파일은 함께 올리지 않습니다.

1. GitHub에서 `tisc2026ai-create` 계정으로 로그인하고 `tisc-booth-notes` 저장소를 만듭니다. 무료 계정의 Pages 사용은 공개 저장소를 기준으로 합니다. 계정·조직의 요금제에 따른 공개 범위는 [GitHub 공식 안내](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)를 확인하세요.
2. 이 디렉터리의 소스를 저장소의 `main` 브랜치에 올립니다. 숨김 경로인 `.github/workflows/pages.yml`도 포함해야 합니다.
3. 저장소 **Settings → Pages → Build and deployment → Source**에서 **GitHub Actions**를 선택합니다. [게시 소스 설정](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)
4. **Actions → Publish consultation recorder → Run workflow**를 실행하거나 `main`에 변경을 푸시합니다.
5. 검사가 통과하고 배포가 완료되면 Actions의 배포 주소를 엽니다. 예상 주소는 `https://tisc2026ai-create.github.io/tisc-booth-notes/`이며 실제 게시 완료 전에는 사용할 수 없습니다.

워크플로는 먼저 검사를 실행하고 공개 화면 파일만 `_site`로 복사해 게시합니다. README·검사 코드·GitHub 설정은 게시 결과에 들어가지 않습니다. GitHub의 [공식 Pages 워크플로 구성](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)에 따라 `github-pages` 환경과 `pages: write`, `id-token: write` 권한을 사용합니다. 저장소마다 GitHub가 제공하는 `GITHUB_TOKEN`을 사용하므로 별도 인증 토큰을 소스에 넣지 않습니다.

소스 업로드 권한은 GitHub의 공식 로그인·인증 흐름으로 연결하세요. 계정 이메일만으로 저장소 변경 권한이 생기지는 않습니다. 비밀번호, 개인 액세스 토큰, 복구 코드를 채팅이나 저장소에 넣지 마세요.

## 보관 범위

웹 화면에는 로그인과 기기 간 자동 동기화가 없습니다. 고객 기록이 온라인에 올라가는 구조도 아닙니다. 기기를 사용하는 사람이 해당 브라우저의 기록을 열 수 있으므로 업무용 기기를 사용하고 기기 잠금을 설정하세요.

브라우저 데이터 삭제·기기 분실·저장 공간 부족으로 로컬 기록이 사라지거나 저장에 실패할 수 있습니다. 내보내기가 끝나도 기기에만 두지 말고 별도 위치에 복사하고, 삭제 전에는 다른 브라우저나 PC에서 가져오기를 확인하세요. ZIP에는 고객 정보가 들어 있으며 암호화되지 않으므로 사내에서 정한 보관 위치로 전달해야 합니다.

Chrome의 `캐시된 이미지 및 파일`만 지우는 것과 `쿠키 및 기타 사이트 데이터`를 지우는 것은 다릅니다. 후자는 IndexedDB의 상담·사진도 삭제합니다. 현재 사용하는 `navigator.storage.persist()`는 브라우저가 저장 공간 부족 때문에 자동으로 자료를 정리하는 위험을 줄이기 위한 요청이며, 사용자의 명시적인 사이트 데이터 삭제는 막지 못합니다. [Chrome의 삭제 항목 안내](https://support.google.com/chrome/answer/2392709/)와 [영구 저장 안내](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)를 참고하세요.

사이트 데이터를 지운 뒤에도 자동으로 복구하려면 브라우저 밖의 저장소가 필요합니다. GitHub Pages는 화면을 배포하며 현재 사이트에는 서버 저장·로그인·자동 동기화가 없습니다. 자동 보관을 추가하려면 로그인과 HTTPS가 있는 서버에 기록·사진을 저장하고, 서버 저장 완료 여부를 표시하며, 오프라인 입력은 연결 복구 후 전송하도록 구성해야 합니다. 지금은 `모든 날짜 ZIP 백업`을 브라우저 밖에 저장한 뒤 `기록 ZIP 가져오기`로 복원할 수 있습니다. 브라우저 데이터 삭제 전에 다운로드한 ZIP 파일이 실제로 열리는지 확인하세요.

명함은 작은 글씨 판독이 가능하도록 보관 품질을 확인하세요. 저장소의 `.gitignore`는 흔한 사진·녹음·내보내기 파일을 제외하지만 강제로 추가하거나 이름을 바꾼 모든 파일까지 막아 주지는 않습니다. 고객 데이터는 처음부터 소스 디렉터리 밖에 보관하세요.
